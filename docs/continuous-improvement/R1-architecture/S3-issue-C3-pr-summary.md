## 2. The two decisions and the recorded stance (provenance)

1. **M2 — `uses` REMOVED, not wired** (owner decision, **2026-11-28**): the field, the seed counts, the "42× used" display, and the uses-based sort are gone; `phrasesFor` is pinned-first then insertion order; the `settingsUsed` ARB key is removed from all three locales. S01 M2 offered "wire or remove — a product decision, flag it to the owner"; the owner chose remove-until-real. Every test-contract change this forces is enumerated in §4.
2. **M5 — stable id per `Phrase`** (S02/S01 §4 step 4): the id is a per-list monotonic **int** (`maxId + 1` in `add`, highest-existing+1 in the migration, 0–7 in the seeds). S02 prescribed "stable id" without a type; int is the minimal choice — ids only ever address a row inside its own language list, so cross-language uniqueness is not needed.
3. **Atomicity stance — option (a), recorded not implicit** (S02 + conductor): keep the multi-key language-set writes and rely on the existing Q17 load-time snap-back. Candidate (b) — folding `main_lang`+`second_lang` into one `language_set` key — is **not implemented** and is recorded in `storage_keys.dart`'s doc comment as the candidate for the first migration that needs to touch the language keys.

## 3. Design notes the gatekeeper should scrutinize

1. **Version-last, crash-safe migration.** Steps are pure and idempotent; `schema_version` is written only after every step succeeded. Pinned two ways: `storage_service_test`'s "failed migration write leaves the marker unwritten … next init converges" (channel-level disk assertions), and `storage_keys_test`'s interrupted-migration re-run. **Ordering rule pinned:** main.dart awaits `storage.init()` before any controller is constructed/`load()`ed (verified by inspection — `await storage.init()` precedes the controller block), and both the unit suite ("a v1 blob is migrated before load") and the behavior suite ("a v1 store is migrated before the controller loads") pin it end-to-end: a v1 blob restores *only* if the migration ran first, otherwise the strict `fromJson` routes it to the corrupt/re-seed path.
2. **The write seam rethrows after capturing.** S02 says "route failures to the scope", and the banner needs `_persist`'s failure path — so `_watch` captures **and rethrows**. Fire-and-forget call sites (the 8 settings setters, `_persistPair`, `setLanguage`) keep today's unhandled-error surface, now preceded by a `storage/write` capture that names the key. If the preference had been swallow-after-capture, the banner channel could not exist; the rethrow is the deliberate half of the design.
3. **Corrupt-blob quarantine lives in the controller's catch, the migration only skips.** S02 item 2's phrase "corrupt-blob handling becomes one place" is satisfied as: the migration treats an undecodable blob as *not migratable* and leaves it **byte-identical** (a migration must not destroy evidence it cannot parse), and the one per-controller `try/catch` that already existed owns backup + telemetry + re-seed. The backup is a true **rename**: one `setString` to `phrases_{lang}.corrupt` (self-capping — the single slot per language is overwritten, never appended) plus `remove` of the original key, so the next boot seeds instead of re-reporting.
4. **`tagKeyAllowlist` gained `storage_key`.** The S02 instruction "tags = key name only" needs the tag *key* allowlisted or the filter strips it; key names are fixed literals (`phrases_en`, `dark_mode`), never child content. `storage/write` is NOT in `_suppressMessageScopes`: the plugin's write-failure messages are fixed strings, and the standard redaction still runs — the unit canary proves the written value never reaches any payload field.
5. **The persist queue (beyond-verbatim addition).** First gate run exposed a real flaw in my own item-5 check: two overlapping `_persist`s made the read-back compare persist #1's raw against a store persist #2 had already updated — a false "round-trip mismatch" (debug noise, seen live in the first run's log). Fix: persists serialize through a one-slot future queue, so each write *and its check* completes before the next starts. Side benefits: the store's snapshot is always the newest one in order, and save-failure transitions fire in mutation order. `_persist` never throws, so a failed write cannot wedge the queue.
6. **Migration write failures are init failures, not write-seam events.** `runMigrations` writes through `SharedPreferences` directly; a failure propagates out of `init()` into main.dart's existing `storage/init` capture. Steady-state writes go through the instrumented seam. This split is deliberate: a failed migration means the app cannot trust its store at all (rethrow → fail fast), while a failed steady-state write is observable + recoverable.
7. **Item 5 (debug round-trip) — implemented, not skipped.** Debug-only, after a *successful* persist: `reload()` (bypasses the plugin's in-memory cache — a successful-looking call that never reached disk would otherwise read back healthy), compare, `debugPrint` **lengths only, never content**. It never throws and never touches the banner state (a mismatch is not a save failure — the write succeeded). Pinned by its own unit test with a store that corrupts after write.
